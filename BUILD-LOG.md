## 4. Tech stack & constraints

- **Framework:** Next.js (App Router), TypeScript. **`next.config.mjs` has `output: 'export'` — this is mandatory, not optional.** Do not add ISR, `revalidate`, or any server-rendering feature without checking history first.
- **ISR ban:** ISR was tried for 447 stub universities to cut build time (commit `88665053`, 83% build-time reduction), then reverted to pure SSG (`9261fe49`), then explicitly re-pinned with a comment (`19ebb62b`: *"static export is mandatory (ISR causes account bans)"*). **Never re-introduce ISR on this project** — it has caused hosting account bans before. If build time becomes a problem again, solve it a different way (stub/prune pages, parallelize the build, etc.), not with ISR.
- **The BOM env-var lesson (verified 2026-07-06/07):** All six `NEXT_PUBLIC_FIREBASE_*` values in the **Vercel dashboard's Environment Variables** had a leading UTF-8 BOM (U+FEFF), pasted in from a Windows/Notepad source. Because `output: 'export'` inlines env vars into the client bundle at build time, the BOM landed directly in the shipped Firebase config strings. The corrupted `authDomain`/`apiKey` made the Firebase SDK throw synchronously during internal URL construction — **before any network request was ever sent** — which Firebase surfaced as a generic `auth/network-request-failed` on `/student-login`. Confirmed via headless network capture: zero `googleapis.com` requests were dispatched, which is what distinguished it from a real CSP/network block. **Fix:** re-type Vercel env var values by hand; never paste from Notepad or another Windows-saved text file. **Symptom to recognize this again:** an SDK-level auth error with literally zero outgoing network requests. (Separately, unrelated: 115/132 course-page `.tsx` source files carry a leading BOM — harmless, source-only, stripped by the bundler; a cosmetic cleanup candidate, not the same issue.)
- **Auth/DB:** Firebase Auth (email/password + phone/OTP) + Firestore, client SDK in `lib/firebase.ts`. CSP in `next.config.mjs` allowlists `*.googleapis.com`, `*.firebase.com`, `*.firebaseio.com`, `*.firebaseapp.com`. Cloud Functions live in `functions/` (Blaze-only — see §1).
- **Hosting:** **Vercel is the active deploy target** — confirmed via `.vercel/project.json` (`projectName: "jaivik-seo"`). `netlify.toml` and a "fix: add Netlify Next.js config" commit exist in history but appear to be an earlier/parallel attempt, not the current live host — don't assume Netlify is live without checking the Vercel dashboard first. `firebase.json` only configures Cloud Functions deployment (`firebase deploy --only functions`), not hosting.
- **`.vercelignore` disables `.gitignore` entirely — found 2026-07-28, fixed same day.** Vercel's documented behavior: once a `.vercelignore` file exists, Vercel CLI deploys stop falling back to `.gitignore` at all — only `.vercelignore`'s own patterns apply. This project's `.vercelignore` only listed `leads/`, `.next/`, `node_modules/`, `*.log`, so everything else gitignored locally (`/out/`, `.env.local`, `.vercel/`, `*.tsbuildinfo`, `public/search-index.json`) was being swept into every `vercel --prod` CLI upload. The stale local `out/` directory (a leftover `next build`/export run, 42,647 files / 4.6GB) turned out to be the entire cause of an abnormal 785MB deploy tgz (compressed) that also blew past Vercel CLI's 15,000-file upload limit on 2026-07-28's pause-recovery deploy. **Fix:** `.vercelignore` now explicitly mirrors the relevant `.gitignore` entries (`/out/`, `/build`, `.env`/`.env*.local`, `.vercel`, `*.tsbuildinfo`, `next-env.d.ts`, `public/search-index.json`) plus `crawl-logs/`/`data/ug-crawl/` (raw crawl scratch data, added to both ignore files, not imported by any page). Uploading `.env.local` in particular was a real secrets-exposure risk, not just bloat. **Verified:** `tsc --noEmit` clean, next webhook-triggered build (unaffected by `.vercelignore`, which only matters for the CLI-upload path) reached Ready normally, `audit-broken-links.js` → 0 broken, live homepage/course-page spot-check → 200. **Rule going forward: any time something is added to `.gitignore`, check whether it also needs adding to `.vercelignore`** — they are not automatically in sync, and `.vercelignore`'s mere existence means `.gitignore` is never consulted as a fallback.
- **Vercel pause/resume, 2026-07-28:** the project was paused ~2026-07-20 and the GitHub→Vercel webhook stopped auto-deploying pushes to `main` — one commit (`71ae61b2`) sat pending on `main` for 8 days with no live effect. After the account resumed on Pro, that pending commit was deployed manually via `vercel --prod --archive=tgz` from the repo root (the plain `vercel --prod` file-by-file upload fails above 15,000 files — this project has 44k+ local files — `--archive=tgz` bundles them into one upload instead). **Confirmed the webhook is reconnected and working again**: a trivial follow-up commit pushed straight to `main` auto-triggered a new Building deployment within ~20s, with the `jaivik-seo-git-main-*` alias that's specific to git-integration builds (a `vercel --prod` CLI deploy never gets that alias). **Going forward: just `git push` to `main` as usual — no need for manual `vercel --prod` deploys** unless the webhook breaks again (check `vercel ls` a minute after pushing; if nothing new appears Building, the webhook is down again and a manual `vercel --prod --archive=tgz` deploy is the fallback). **Deploy-path difference that matters for `app/sitemap.ts`'s git-derived lastmod (see §1 "Sitemap lastmod"):** a CLI `vercel --prod` upload gives the build container no usable git history at all (0 lastmod tags produced); a webhook-triggered build gives it a real but shallow git clone (lastmod present and correctly varies for recently-changed files, but old/untouched files collapse onto one shared boundary date rather than their true older date). This is one more reason to prefer the webhook path over manual CLI deploys now that it's confirmed working.
- **TypeScript check at build:** `next.config.mjs` sets `typescript: { ignoreBuildErrors: true }` (added to avoid an OOM on Vercel during type-check — commit `d7d74b5d`). This means `npm run build` will **not** catch type errors — always run `npx tsc --noEmit` separately before pushing.
- **"No invented course data — ever" rule.** This is the single most load-bearing rule on this project. Every fee, IELTS score, visa-pathway detail, or salary figure shown to a student must trace back to a real field in a `data/*.ts` file or a verifiable, checkable computation over one (currency conversion, duration-based visa-length rules, etc.). When backing data is missing, the correct behavior is to **skip that section/fact entirely**, not to write a plausible-sounding placeholder, "varies", or generic industry-average number. See `DATA-AUDIT.md`'s REAL/CURATED classification and `lib/course-faqs.ts` / `lib/course-sections.ts` for the reference implementation of "real-data-only, skip-on-missing" content generation.
- **SEO metadata hygiene (fixed 2026-07-15, GSC coverage cleanup):**
  - **Every page's canonical comes from `alternates.canonical` in its own `Metadata` object** — `app/layout.tsx` (root) sets no canonical at all, so any page that doesn't call `lib/seo.ts`'s `buildMetadata()` (or set `alternates.canonical` itself) silently ships with **zero** canonical tag. Found 8 real pages missing one entirely: `/`, `/contact`, `/cost-calculator`, `/eligibility-checker`, `/find-my-course`, `/ielts-coaching`, `/scholarships`, `/terms` — all fixed by adding a canonical (5 of them — contact/cost-calculator/eligibility-checker/scholarships, plus the pre-existing `/dashboard` pattern — needed a sibling `layout.tsx` instead of `export const metadata` in `page.tsx`, because **a `'use client'` page.tsx cannot export Next.js metadata at all**; a Server Component `layout.tsx` next to it can, and Next.js merges it in). **When adding any new top-level route, check it has a canonical — `buildMetadata()` handles it automatically, a bare custom `metadata` object does not.**
  - **Client-component pages need a sibling `layout.tsx` for metadata/robots**, not a code change to the page itself. Precedent: `app/dashboard/layout.tsx`. Used for `app/contact`, `app/cost-calculator`, `app/eligibility-checker`, `app/scholarships` (real content → indexed, real title/description via `buildMetadata()`) and `app/thank-you`, `app/student-portal/verify` (thin/duplicate content → `noindex`).
  - **Pruning a university's course data must ship redirects in the same commit, not a follow-up.** The 2026-07-13 CURATED-data prune (28 universities, see §3) deleted `/universities/<slug>/courses/*` route trees but didn't add redirects for them (only the one VUW duplicate-slug case got a redirect, since that was the specific bug being fixed that day) — those pages had been indexed by Google, so they surfaced as 404/"other 4xx" in the next GSC crawl report. Fixed 2026-07-15 with 25 pairs of wildcard redirects (one pair per pruned university: `/courses` and `/courses/:path*` → that university's real profile page, a same-institution real page under a different slug, or a country page as last resort — **never the homepage**). **These were originally added to `next.config.mjs` and were silently dead in production — see §4 "Redirects/headers in `next.config.mjs` don't work on this deployment" — all 75 redirect rules now live in `vercel.json` instead.** **Going forward: any time a university/course route is deleted, add its redirect to `vercel.json`** (not `next.config.mjs`), following this pattern.
  - **Always grep for stray hardcoded internal links after renaming/pruning a slug.** `app/eligibility-checker/page.tsx` had a hand-written `UNI_REQS` array (independent of `data/universities.ts`) with 5 dead slugs — 3 from the prune (`georgia-institute-of-technology`, `delft-university-of-technology`, `victoria-university-of-wellington` — should've been `georgia-tech`, `tu-delft`, `victoria-university-wellington`) and 2 pre-existing/unrelated (`massachusetts-institute-of-technology` should've been `mit-massachusetts`; `university-of-dubai` didn't exist under any slug — removed the row rather than invent a substitute). Check with: `grep -rhoE "/universities/[a-z0-9-]+" app components lib data --include="*.tsx" --include="*.ts" | sort -u`, then diff against `data/universities.ts`'s real slugs.
  - **The sitemap needs no manual pruning** — `app/sitemap.ts` and `app/sitemap-courses.xml/route.ts` both build their course-page list by checking whether `app/universities/<slug>/courses/` exists on disk, so deleting a university's route folder (as the prune already does) automatically removes it from both sitemaps with no separate step required.
- **Composite dynamic-segment gotcha (found 2026-07-15, building the decision hubs):** A route folder named with a static prefix baked into the dynamic segment — e.g. `app/cheapest-universities-[country]/page.tsx`, intended to serve `/cheapest-universities-uk` — **builds successfully and passes `tsc`, but under `output: 'export'` only emits one literal file named `cheapest-universities-[country].html`**. `generateStaticParams()` is silently not enumerated into per-value static files for this segment shape; no build error, no warning — it just silently produces the wrong output. Confirmed by inspecting `.next/server/app/` and `out/` directly after a full build, not from the build log (which shows no error). Pure `[param]` segments (a full segment, no baked-in prefix) do **not** have this problem — `app/courses-with-psw/[country]/page.tsx` (nested) and `app/[decisionSlug]/page.tsx` (root-level) both enumerate correctly. **Fix used:** merge any URL shape that needs a static-prefix-plus-dynamic-suffix into an existing full-segment dynamic route, parsing the distinguishing prefix/suffix out of the whole slug string in code (see `app/[decisionSlug]/page.tsx`, which handles both `cheapest-universities-<country>` and `<country>-under-<band>-lakh` from one `[decisionSlug]` param via regex/lookup dispatch). **Rule going forward: never create a route folder whose name mixes literal text with a `[bracket]` — always use a full `[param]` segment and parse the literal prefix/suffix in code.** After any new dynamic route, verify with `find out -iname "<route-prefix>*"` that real per-value files were produced, not a literal bracket-named file.
- **Redirects/headers in `next.config.mjs` don't work on this deployment — found 2026-07-16, via the ANU civil-engineering redirect (commit `04863b96`) 404ing live despite passing every local check.** Next.js only applies `redirects()`/`rewrites()`/`headers()` from `next.config.mjs` when `output: 'export'` is set **if the build detects `hasNextSupport`** — internally gated on `process.env.NOW_BUILDER`, set only by Vercel's first-party `@vercel/next` framework builder. This project's Vercel deployment doesn't go through that path, so the check is false and Next.js silently no-ops all three config functions (confirmed locally: `npm run build` prints `⚠ Specified "headers" will not automatically work with "output: export"` — the same warning would have fired for `redirects()` before this fix removed it). **This means the entire 75-rule `redirects()` array in `next.config.mjs` — including all 25 pairs from the 2026-07-15 GSC crawl-budget fix (`eb3177f9`) — was dead in production the whole time**, despite `npx tsc --noEmit`, `npm run build`, and `.next/routes-manifest.json` all looking correct; those checks validate the Next.js build artifact, not what Vercel actually serves for this project. **Fix:** all 75 redirects moved to `vercel.json` (`{ "redirects": [...] }`, same `source`/`destination`/`permanent` shape as Next's format — no path-pattern conversion needed), and `redirects()` deleted from `next.config.mjs` entirely. **`headers()` (CSP, X-Frame-Options, etc.) in `next.config.mjs` has the identical bug and was NOT fixed here** (out of scope for this task) — those security headers are very likely also absent in production; verify with real HTTP headers on a live page before trusting `next.config.mjs`'s `headers()` block again. **Rule going forward: any new redirect goes in `vercel.json`, never `next.config.mjs`. To verify a redirect actually works, curl/check the live production URL — a clean local build proves nothing about what Vercel serves for this project.** **Update 2026-07-20:** the same rule now applies to headers too — `vercel.json` got its first `headers` block (`Referrer-Policy`, `Permissions-Policy`; see §1 "External-audit polish pass"), confirmed live via `curl -I`. `next.config.mjs`'s `headers()` (CSP, X-Content-Type-Options, X-Frame-Options) is still unfixed/dead — any future header change should go in `vercel.json`, matching redirects.

**Correction, 2026-07-28 — the claim directly above about `next.config.mjs`'s `headers()` is no longer true and was wrong to trust without re-checking.** While diagnosing why GA4 wasn't recording traffic (see §1 "GA4 analytics — CSP fix + conversion events"), a live `curl -I` on production showed a full `Content-Security-Policy` header (plus `X-Content-Type-Options`/`X-Frame-Options`) that matches `next.config.mjs`'s `headers()` function byte-for-byte — confirmed reproducible across 3 different pages, not a cache fluke. `vercel.json` has never defined a CSP at all (only `Referrer-Policy`/`Permissions-Policy`), so there is no ambiguity about the source: **`next.config.mjs`'s `headers()` — including its CSP — is genuinely live in production right now**, contrary to the 2026-07-16 finding this section is attached to. The exact cause of the behavior change between then and now wasn't tracked down (candidates: the Vercel Pro-plan resume changed framework-detection/`hasNextSupport` behavior for this project; a Vercel platform-side change to how `output: 'export'` + `headers()` is handled) — but the CURRENT, confirmed-live reality is what matters. **Rule going forward: don't trust this file's historical claims about which config mechanism is "dead" without a fresh live `curl -I` check first — Vercel's handling of `next.config.mjs` vs `vercel.json` for this project has changed at least once already and could again.** Re-checked redirects specifically today (not just assumed): `next.config.mjs` no longer has a `redirects()` function at all (deleted as part of the 2026-07-16 fix), and a live `curl -I` on a known `vercel.json` redirect (`/courses/mba-master-of-business-administration` → `/mba-abroad-for-indian-students`) still returns a correct 308 — so redirects remain correctly served from `vercel.json` regardless of today's headers()/CSP correction.

## 5. Deploy checklist

Run all of these before any push that touches `app/`, `components/`, `lib/`, or `data/`:

1. `npx tsc --noEmit` — must be clean. (Build-time type-check is disabled — see §4 — so this is the only type-safety gate.)
2. `npm run build` — full static export must succeed. This is a large static-export site (7000+ pages as of last count); expect several minutes.
3. **Headless HTML check** — since there's no dedicated script for this yet, grep the exported HTML directly in `out/<path>/<slug>.html` (flat files, not `<slug>/index.html`) for whatever the change was meant to add/fix, across at least 2-3 different countries if the change is country-sensitive. Any embedded `<script type="application/ld+json">` blocks should be extracted and `JSON.parse`'d to confirm they're valid, not just present. Note: React splits interpolated text across sibling nodes/HTML comments in the exported output — check for substrings with independent `.includes()` calls rather than one contiguous regex spanning a static heading + a JSX variable.
4. `node scripts/audit-broken-links.js` — must report 0 broken links (compares every university-profile course listing link against every `generateStaticParams()`-generated page).
5. Confirm the git diff/staged files are scoped to the actual change — this repo routinely has unrelated in-progress/uncommitted work sitting in the tree (see §2 item 7); never `git add -A`. Stage explicit file lists.
6. Push to `main` — Vercel auto-deploys from `main`.
7. **Update this file (`BUILD-LOG.md`)** with whatever changed: new/changed feature rows in §1, new bugs found in §2, new data waves in §3, new constraints learned in §4.
